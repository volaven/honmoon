결론: 기능 전달 방식은 큰 페이지의 전체 접근성 정보보다 작았지만, 모든 페이지·도구·작업에서 더 저렴하다고 입증하지는 못했습니다. 모델이 기능 소스코드를 읽는 구조가 아니라 도구 스키마와 기능 JSON을 읽는 구조입니다.

단위는 토큰입니다. 각 페이지를 실제 HONMOON 내장 Chromium에서 3회 관측했습니다. 전체 AX는 agent-browser snapshot, 압축 AX는 snapshot -i -c, 기능 목록은 실제 Orchestrator capabilities.list 응답입니다. 서로 같은 페이지·같은 시점의 수집 문자열을 비교했습니다.

현재 8개 Codex 도구 정의 JSON은 별도 626토큰입니다. 검색/상세 보조 도구 추가 후 도구 스키마를 갱신했으며, 페이지 문자열은 위 수집본을 유지했습니다. 도구 정의 이외의 시스템 지시·사용자 프롬프트·추론·반복 대화 컨텍스트·이미지·추가 본문 관측 비용은 이 표에 없습니다. 따라서 청구량 비교로 해석하면 안 됩니다.

MDN·위키백과 첫 기능 목록은 전체 AX보다 각각 58.8%, 61.2% 작습니다. 압축 조작 AX보다 각각 11.1%, 8.2% 큽니다. 작은 시작 페이지는 전체 AX 26토큰에 비해 기능 목록 110토큰으로 오히려 커집니다.

## 재현 및 한계

`npm run build` → `npm run verify -- --tokens` → `python -m pip install -r benchmarks/requirements.txt` → `python benchmarks/count_tokens.py`. 스키마만 최신으로 갱신하려면 `npx tsx scripts/refresh-token-schemas.ts`를 실행합니다.

[OpenAI tiktoken](https://github.com/openai/tiktoken)의 0.12.0 / o200k_base로 문자열을 정확히 세었습니다. 실제 모델별 토크나이저 및 청구 규칙과 같다는 보장은 없습니다. 특정 모델의 실제 사용량은 앱이 수신하는 Codex tokenUsage 기록으로 별도 측정해야 합니다.

Luna의 정확도 향상, Flow/Grok 각 10개 작업의 입력 중앙값 40% 절감·완료율 저하 5%p 이내는 실계정 작업을 수행하기 전까지 미검증입니다. 로컬 로그인 클릭에 실패한 초기 수집 실행은 제외했고, 최종 표는 동작을 변경하지 않는 4개 관측 화면으로 구성했습니다.
